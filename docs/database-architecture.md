# Database architecture

## Purpose

The first database version supports a single-day transport simulation with two
planning phases:

1. Generate or import stops.
2. Generate synthetic passengers and their trip requests for one service day.

The schema also reserves a small, explicit place for the optimizer output so
that the generated timetable can later be queried by the passenger application.

SQLite is the initial database. The schema uses ordinary relational types and
foreign keys so it can be moved to PostgreSQL later without redesigning the
domain model.

## Data flow

```text
stops
  |
  v
simulation_scenarios -> passengers -> trip_requests
  |                                      |
  v                                      v
route_plans -> routes -> route_stops <- assignments
                 |
                 v
              vehicles
```

Stops exist independently of a simulation. All generated passengers, requests,
and optimizer results belong to one simulation scenario.

## Core conventions

- Use integer primary keys generated by the database.
- Store all timestamps as timezone-aware values normalized to UTC.
- Store `service_date` as the local calendar date in the `Europe/Warsaw` time
  zone.
- Use lowercase string values for domain categories.
- Enable SQLite foreign-key enforcement for every connection.
- Do not store names, addresses, or other real personal data for synthetic
  passengers.
- Do not commit the local SQLite database file to source control.

## Tables

### `stops`

Stores the hub and local pickup stops. Stops are reference data and can be
shared by multiple simulation scenarios.

| Column | Type | Rules | Meaning |
| --- | --- | --- | --- |
| `id` | integer | primary key | Internal stop identifier |
| `name` | text | required | Human-readable stop name |
| `locality` | text | required | City, town, or village containing the stop |
| `latitude` | real | required, -90 to 90 | WGS84 latitude |
| `longitude` | real | required, -180 to 180 | WGS84 longitude |
| `kind` | text | required | `main_hub` or `local` |
| `source` | text | required | `synthetic`, `osm`, or `manual` |
| `source_reference` | text | optional | Stable identifier in the source dataset |
| `is_active` | boolean | required, default true | Whether generators may use the stop |
| `created_at` | datetime | required | Creation time |

Constraints:

- `(source, source_reference)` is unique when `source_reference` is present.
- Coordinates must be in valid WGS84 ranges.
- Several stops may use `main_hub`; these are destination stops in larger towns.
- A simulation selects one of them as its default hub but requests may target any hub.

Recommended indexes:

- `stops(kind, is_active)`
- `stops(source, source_reference)`

### `simulation_scenarios`

Represents one independently reproducible single-day simulation. Multiple
scenarios may use the same service date.

| Column | Type | Rules | Meaning |
| --- | --- | --- | --- |
| `id` | integer | primary key | Scenario identifier |
| `name` | text | required | Display name, for example `Typical Monday` |
| `service_date` | date | required | Day being simulated |
| `main_hub_stop_id` | integer | foreign key to `stops` | Destination hub for inbound requests |
| `planning_cutoff_at` | datetime | required | Deadline for planned requests |
| `random_seed` | integer | required | Makes generated demand reproducible |
| `status` | text | required | `draft`, `demand_ready`, `planned`, or `completed` |
| `created_at` | datetime | required | Creation time |

Recommended indexes:

- `simulation_scenarios(service_date, status)`

### `passengers`

Stores synthetic people generated for one scenario. A passenger profile is
separate from the trip purpose: a senior can travel for shopping or healthcare,
for example.

| Column | Type | Rules | Meaning |
| --- | --- | --- | --- |
| `id` | integer | primary key | Synthetic passenger identifier |
| `scenario_id` | integer | foreign key to `simulation_scenarios` | Owning simulation |
| `persona_type` | text | required | `student`, `worker`, `senior`, or `occasional` |
| `home_stop_id` | integer | foreign key to `stops` | Default local pickup stop |
| `reduced_mobility` | boolean | required, default false | Mobility assistance flag |
| `created_at` | datetime | required | Creation time |

Recommended indexes:

- `passengers(scenario_id, persona_type)`
- `passengers(scenario_id, home_stop_id)`

Deleting a scenario should delete its synthetic passengers.

### `trip_requests`

Stores the demand consumed by the optimizer. An inbound request normally uses
the passenger's home stop as its origin and the scenario's main hub as its
destination.

| Column | Type | Rules | Meaning |
| --- | --- | --- | --- |
| `id` | integer | primary key | Request identifier |
| `scenario_id` | integer | foreign key to `simulation_scenarios` | Owning simulation |
| `passenger_id` | integer | foreign key to `passengers` | Requesting passenger |
| `origin_stop_id` | integer | foreign key to `stops` | Boarding stop |
| `destination_stop_id` | integer | foreign key to `stops` | Alighting stop |
| `trip_purpose` | text | required | `school`, `work`, `shopping`, `healthcare`, `leisure`, or `other` |
| `desired_arrival_at` | datetime | optional | Latest preferred arrival time |
| `desired_departure_at` | datetime | optional | Earliest preferred departure time |
| `passenger_count` | integer | required, default 1, greater than 0 | Seats requested |
| `request_source` | text | required | `planned` or `late` |
| `status` | text | required | `pending`, `assigned`, `rejected`, or `cancelled` |
| `submitted_at` | datetime | required | Time at which demand was submitted |

Constraints:

- Origin and destination must be different.
- At least one of `desired_arrival_at` and `desired_departure_at` must be set.
- Planned requests must have `submitted_at <= planning_cutoff_at`; enforce this
  in application logic because it crosses table boundaries.
- The initial inbound-demand generator sets `desired_arrival_at` and leaves
  `desired_departure_at` empty.

Recommended indexes:

- `trip_requests(scenario_id, status, desired_arrival_at)`
- `trip_requests(origin_stop_id, destination_stop_id)`
- `trip_requests(passenger_id)`

Deleting a scenario should delete its requests.

## Optimizer output tables

These tables do not need to be populated by the first stop or passenger
generator, but their structure defines the output contract for the routing
engine.

### `vehicles`

| Column | Type | Rules | Meaning |
| --- | --- | --- | --- |
| `id` | integer | primary key | Vehicle identifier |
| `code` | text | required, unique | Stable code such as `bus-01` |
| `capacity` | integer | required, greater than 0 | Available passenger seats |
| `is_active` | boolean | required, default true | Availability for planning |

### `route_plans`

A scenario may have several optimizer runs, but only one should be published.
This makes it possible to rerun the optimizer without overwriting an earlier
result.

| Column | Type | Rules | Meaning |
| --- | --- | --- | --- |
| `id` | integer | primary key | Plan identifier |
| `scenario_id` | integer | foreign key to `simulation_scenarios` | Planned simulation |
| `status` | text | required | `draft`, `published`, or `superseded` |
| `engine_version` | text | required | Optimizer version or configuration label |
| `created_at` | datetime | required | Optimizer run time |

Recommended index:

- `route_plans(scenario_id, status)`

### `routes`

| Column | Type | Rules | Meaning |
| --- | --- | --- | --- |
| `id` | integer | primary key | Route identifier |
| `route_plan_id` | integer | foreign key to `route_plans` | Owning plan |
| `vehicle_id` | integer | foreign key to `vehicles` | Assigned vehicle |
| `starts_at` | datetime | required | Planned route start |
| `ends_at` | datetime | required | Planned route end |
| `total_travel_seconds` | integer | required, non-negative | Planned driving time |

Recommended index:

- `routes(route_plan_id, vehicle_id)`

### `route_stops`

Stores the actual timetable. One row represents one visit of one route to one
stop. A route may visit the same stop more than once.

| Column | Type | Rules | Meaning |
| --- | --- | --- | --- |
| `id` | integer | primary key | Route-stop visit identifier |
| `route_id` | integer | foreign key to `routes` | Owning route |
| `stop_id` | integer | foreign key to `stops` | Visited stop |
| `stop_sequence` | integer | required, zero or greater | Visit order |
| `planned_arrival_at` | datetime | required | Planned arrival |
| `planned_departure_at` | datetime | required | Planned departure |
| `occupancy_after_departure` | integer | required, non-negative | Seats occupied after leaving |

Constraints:

- `(route_id, stop_sequence)` must be unique.
- Departure cannot be earlier than arrival.

Recommended indexes:

- `route_stops(route_id, stop_sequence)`
- `route_stops(stop_id, planned_departure_at)`

### `assignments`

Links a passenger request to the two visits at which the passenger boards and
leaves the vehicle. The pickup time is read from the boarding route stop rather
than duplicated for every passenger.

| Column | Type | Rules | Meaning |
| --- | --- | --- | --- |
| `id` | integer | primary key | Assignment identifier |
| `request_id` | integer | foreign key to `trip_requests`, unique | Assigned demand |
| `boarding_route_stop_id` | integer | foreign key to `route_stops` | Boarding visit |
| `alighting_route_stop_id` | integer | foreign key to `route_stops` | Alighting visit |
| `status` | text | required | `reserved`, `confirmed`, `completed`, or `cancelled` |
| `created_at` | datetime | required | Assignment time |

Application validation must ensure that both route-stop visits belong to the
same route and that the boarding sequence is lower than the alighting sequence.

Recommended indexes:

- `assignments(boarding_route_stop_id)`
- `assignments(alighting_route_stop_id)`

## Generation workflow

### Stage 1: stops

1. Insert one stop with `kind = main_hub`.
2. Insert additional destination stops with `kind = main_hub` where required.
3. Generate or import local stops with `kind = local`.
4. Validate coordinate ranges and reject duplicate source references.
5. Mark unusable stops as inactive instead of deleting them when simulations
   already reference them.

### Stage 2: passengers and demand

1. Create a `simulation_scenarios` row with its date, cutoff, hub, and random
   seed.
2. Read active local stops.
3. Generate passengers according to configured persona proportions.
4. Assign each passenger a `home_stop_id`.
5. Generate one inbound `trip_requests` row per travelling passenger.
6. Set the request origin to the passenger's home stop and destination to the
   scenario's main hub.
7. Generate `desired_arrival_at` from the distribution appropriate for the
   persona and trip purpose.
8. Commit the generated scenario in one database transaction.
9. Change the scenario status from `draft` to `demand_ready` only after the
   complete generation succeeds.

Using one transaction prevents a failed generator run from leaving a partially
generated population in the database.

### Initial synthetic-demand assumptions

The first generator creates one inbound request per passenger. Origins are
selected from active local stops, while destinations are selected from active
city hubs using distance and city-attractiveness weights.

By default, 75% of passengers select the nearest city and 25% deliberately
select another city. Alternative cities are weighted by distance and city
attractiveness. This represents work, school, healthcare, and personal
preferences that are not explained by distance alone.

| Persona | Share | Main purposes |
| --- | ---: | --- |
| `student` | 30% | School, usually arriving around 07:45 |
| `worker` | 40% | Work, usually arriving around 08:00 |
| `senior` | 20% | Shopping and healthcare during off-peak hours |
| `occasional` | 10% | Shopping, leisure, healthcare, or other |

Times are sampled from bounded normal distributions instead of fixed values.
All generated requests are submitted between 08:00 and the planning cutoff on
the previous day. The scenario's random seed makes the complete generated set
reproducible.

## Late passenger workflow

A request submitted after the cutoff is stored with `request_source = late`.
The first application version must not modify a published route. Instead it:

1. Finds a published route that visits the origin before the destination.
2. Checks capacity for every leg between those visits.
3. Selects the arrival closest to, but not later than, the requested arrival.
4. Creates an assignment if a seat is available, otherwise rejects the request.

Allowing a late request to add a new stop requires schedule recalculation and is
outside the first version.

## Initial implementation boundary

The first database implementation should create and use only:

- `stops`
- `simulation_scenarios`
- `passengers`
- `trip_requests`

The optimizer-output tables should be added immediately after the input
generator is working. Keeping their contract in this document ensures that the
input model will already support that next step.
